# Claude Code 向けプロジェクト指示

このファイルは Claude Code がプロジェクトに入ったとき最初に読むファイルです。
本プロジェクトの**続きを書く**ときは、まず `DEVELOPMENT.md` を読み、現在のフェーズを把握してから作業してください。

## プロジェクト概要

Numeron (3桁の数字当てゲーム) のWebサービス実装。Go + 既存HTMLフロントエンド、将来的に React + TS に移行予定。
ユーザー2万人規模・本気運用・学習目的を兼ねたプロジェクト。

## 最初に必ず読むファイル

1. **`DEVELOPMENT.md`** ← 全フェーズのロードマップ・進捗・設計判断の記録。**最重要**
2. `README.md` ← セットアップ手順
3. `go.mod` ← 依存関係 (基本は標準ライブラリのみ)

## 開発の進め方

このプロジェクトは **フェーズ駆動**で進めています。

- 進行中のフェーズを `DEVELOPMENT.md` で確認
- ユーザーが「フェーズX.Yをやろう」と言ったら、該当する「次セッションへの引き継ぎ」セクションを読んで作業開始
- フェーズ完了時には `DEVELOPMENT.md` の以下を必ず更新:
  - フェーズ一覧のチェックボックス
  - 「現在地」セクション
  - 「設計判断の記録」(新しい判断があれば)
  - 「既知の負債」(解消したものに ✅、新たに発見したものを追加)
  - 「次セッションへの引き継ぎ」(次フェーズの具体作業を記述)
  - 「ファイル構成」(新規ファイルがあれば反映)

## アーキテクチャ原則

```
cmd → adapter → usecase → port → domain
```

- 依存方向は一方向。**下位層は上位層を一切知らない**
- domain層は外部依存ゼロ (DB/HTTP/フレームワーク等を知らない)
- usecase / domain はログを書かない (ロガーを受け取らない)。エラーを返すだけ
- リポジトリは `port` のインターフェース経由。具象実装に直接依存しない

## コーディング規約

- **外部依存は最小化**: 標準ライブラリで完結を優先。新しい依存を入れる前に必要性を議論する
- **テーブル駆動テスト** + **`t.Run` でサブテスト化**
- **`-race` フラグ**で常にテストを走らせる (CIでも必須)
- **エラーは型で表現**: `var ErrXxx = errors.New(...)` + `fmt.Errorf("%w: 詳細", ErrXxx)` + `errors.Is` で判定
- **構造化ログ**: `slog`。usecase / domain では使わない、handler / middleware で出力
- **構造化エラーレスポンス**: `{"error":{"code":"...","message":"...","details":{...}}}`

## テスト戦略

1. domain層: 純粋関数のユニットテスト (カバレッジ 99%+)
2. usecase層: モック port を使ったユニットテスト (90%+)
3. handler層: `httptest.NewServer` で本物のサーバー起動 (95%+)
4. persistence層: フェーズ2.4 で testcontainers + PostgreSQL

## 言語ポリシー

- ユーザーとの対話: **日本語**
- コードコメント: 日本語OK (既存に合わせる)
- 識別子(関数名/変数名): 英語
- エラーメッセージ(ユーザー向け): 日本語
- ログメッセージ(運用者向け): 英語

## やってはいけないこと

- フェーズの順番を勝手に飛ばさない (依存があるため)
- 「既知の負債」リストにあるものを勝手に勘案して大規模リファクタリングしない
- 新しい外部ライブラリを勝手に追加しない (相談する)
- `DEVELOPMENT.md` の更新を忘れない (これがないと次セッションで迷子になる)

## よく使うコマンド

```bash
go test ./... -race -cover           # 全テスト + 競合検出 + カバレッジ
go vet ./...                          # 静的解析
go build -o /tmp/numeron ./cmd/server # ビルド
docker compose up -d                  # PostgreSQL + Redis 起動
docker compose down                   # 停止 (-v でボリュームも削除)
sqlc generate                         # SQL → Go コード生成
migrate -path db/migrations -database "$DATABASE_URL" up   # マイグレーション
```

## 作業の流れ (典型例)

```
ユーザー: 「フェーズ2.3をやろう」

Claude Code:
1. DEVELOPMENT.md を view して該当する引き継ぎセクションを読む
2. 必要なファイルを把握 (例: db/migrations/, db/queries/)
3. 設計判断が必要なら先に相談する (例: BIGSERIAL vs UUID)
4. ユーザーの承認を得たら実装開始
5. テストを書いて pass を確認
6. go test ./... -race で全体回帰確認
7. DEVELOPMENT.md を更新 (フェーズ完了マーク、現在地、次回引き継ぎ等)
8. ユーザーに完了報告と次フェーズへの案内
```
